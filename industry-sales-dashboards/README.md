### Early Smoke Gate

The first task checks the existing schemas, then validates the same job identity and target SQL warehouse and checks remote O2C identifier quoting. It reads at most one qualifying O2C row through the warehouse and writes/reads its original required columns using the actual volume Parquet path (120-second warehouse statement limit). Each other required source has an explicit-column `LIMIT 1` Spark query and a real file write/read; the source query can return zero rows without implying an error. Across all 14 sources, the smoke data is limited to one row per source, not a copy of the source tables. No source values are logged.

Workspace verification does not infer identity from a single `adb-<id>.<shard>` URL pattern. The SDK client must have a trusted HTTPS Azure Databricks origin; the helper then reads `X-Databricks-Org-Id` from the authenticated `/api/2.0/preview/scim/v2/Me` response, the same endpoint/header used by the SDK workspace-ID resolver, and compares it with the validated Spark job workspace ID. Public/alternate hostnames, case and default HTTPS port variations can therefore refer to the same workspace without being rejected by URL shape alone. Missing/mismatched server evidence or a failed verification request stops before any SQL submission; a configured client workspace_id is not accepted as a substitute for server evidence. The independent Spark-versus-warehouse current_user comparison remains mandatory. Logs show only hostname and verified IDs, never credentials or query-string contents. The ACC/PRD warehouse IDs and connection details remain unchanged.

The checked source schemas are registered as empty, session-only fixture views. Every active dataset's original/producer/consumer SQL is then analyzed against those fixtures and the versioned mapping seed, with CTE boundaries rebuilt as typed empty views. All 18 output column-name/type contracts must match. The analyzer rejects leftover qualified source-table references rather than silently running a real source join. This is schema/binding validation, not full dataset execution or KPI equality certification. The local smoke fixture validates the mechanism with real Spark reads/files and 18 small contracts; full native query behavior still needs target acceptance.

Smoke creates no persistent table and never updates result state, receipts, mapping copies or published results. Its scratch is isolated by target and fresh UUID, cleaned on success and retained on failure for diagnostics. Logs identify `smoke_source_started/verified`, `smoke_dataset_started/verified` and final `smoke_checks_passed`, making the failing check visible before production begins. The 1,200-second task limit includes preparation allowance; cold startup must not be assumed to occur outside the task budget. Compare the first `smoke_started` timestamp with run timing before diagnosing a source stall. ACC run 884652521715996 timed out after 10m44s under the former 600-second setting, but its last source-start log was only 167.209 seconds after `smoke_started`; that screenshot does not prove a ten-minute product-hierarchy scan. The new budget does not guarantee completion or a fixed amount of execution time, and queueing/cancellation can affect observed elapsed time. Limits, permissions, syntax, connector reads/writes and type mismatches should fail early; data-dependent errors outside the samples, later executor losses, full-volume performance and full-result parity can still fail during production.

The generated `dashboard_results.json` defines 18 active datasets: nine Open Orders and nine Quotations. `ds_top_late_orders` is required by the overview Top 10/Top 5 tables through the relationship source alias `Top_Late_Orders_CM__YTD`; both the dataset and alias registration are retained. Retirement checks cover relationship aliases as well as technical dataset names. Only the unreferenced `ds_cancellations_trend` is removed. Original captures and all page/widget definitions remain unchanged for audit. Thirteen parameter-free datasets materialize their final, originally filtered/calculated results. Five parameterized datasets preserve the necessary joined row detail and parameter-free calculation boundaries. Their original filters and aggregations remain in the consumer SQL. In particular, segment/country filters still run before quote-level SUM/MAX and COUNT DISTINCT; an All-segments total is not reused as a filtered total. Cancellation date bounds, priority/day buckets, output column names, and native ordering are retained. This produces 21 unique result relations: 13 final outputs and eight supporting relations for five filter-sensitive datasets. A small order-reason lookup is retained where required; this is not a full-source snapshot design.

The Top Orders restoration adds gold `SC_BI_industry_sales_open_orders_ds_top_late_orders_result` and silver `SC_BI_industry_sales_calc_open_orders_ds_top_late_orders_result`. After CI promotion, run the complete refresh job successfully to create/populate them, then apply the two READ-group SELECT declarations through the central access process and refresh both overview tables. This is not an ACL-only release. Do not reconcile against these two names before they exist. The original ranking, period filters and output types are unchanged; browser rendering still requires native acceptance after deployment.

The identical `converted` component in `ds_quotations`, `ds_quotations_detail` and `ds_expiring_quotes` is calculated, written and verified once per job batch. The other two producers load the verified silver rows pinned to that same batch, not the still-published previous gold batch, and establish their own temporary CTE and dataset receipt. All three consumer queries use the same gold result view. Sharing is restricted to this named, independent, fully-qualified calculation with identical parsed SQL; conflicting or CTE-dependent shared definitions fail before writing. Other source reads are not automatically deduplicated.

The producer executes the existing SQL/CTE calculations as the job identity. Computed stages are written to unique Parquet support files in the existing `/Volumes/<catalog>/bronze/bronze_volume/SC_BI_industry_sales_result_scratch/<target>/<batch>/<dashboard>/<dataset>/<stage>` path, then read with the original column types. All but the targeted cancellation calculation run on job Spark; the cancellation exception is described below. This truncates query plans without executor-local checkpoint blocks: later stages can reread cloud-backed files after a worker loss. It does not use DataFrame/RDD checkpoint APIs or create any table, schema, or volume. The verified shared conversion result is already Delta-backed and is read directly by batch ID. A single-row scratch write/read preflight occurs before result/state writes and requires job-identity READ_VOLUME and WRITE_VOLUME plus parent USE privileges. These are engineer/deployment privileges, not reader-group grants. Each successful dataset's files are removed only after its computations/writes/verification finish; failed or interrupted scratch remains for operator review and scoped cleanup. Cleanup failure is logged without changing publication status, and the job never deletes another target/batch's files.

Native duplicate, NULL, decimal and timestamp values are retained. For scratch writes only, Spark's Parquet date/timestamp rebasing is temporarily CORRECTED and restored in a finally block; original old dates are neither filtered nor rewritten. The producer's source date is fixed once at task start. Parameterized consumer date expressions still use their original CURRENT_DATE semantics over the saved input data, so a stale batch does not become fresh merely because the clock changes. Original lookback windows and source joins are not shortened to force lower row counts. Scratch adds file I/O; filter-sensitive details can still contain many qualifying rows and sequential datasets can repeat source reads. This is a worker-loss resilience change, not a guaranteed runtime improvement, cluster restart recovery, or real-data performance certification.

Scratch writes use `mode("error")`, the error-if-present spelling supported by both classic PySpark and the Spark Connect command serializer. The classic-only `errorifexists` alias is not used. Existing paths still fail rather than being overwritten or silently ignored. Preflight failures preserve the original error type, message and chained cause; a client-side mode/serialization failure must not be reported as evidence of missing volume grants. Volume permissions remain a prerequisite, not a diagnosis for every initialization error.

If a scratch write fails while evaluating an upstream query, the helper writes the full original error and `EXPLAIN FORMATTED` plan to a sibling `<stage>.failure.json` file in that batch's scratch folder, outside the Parquet directory. Console `scratch_write_failed` records contain at most 8 KB of UTF-8 JSON, a short error and the diagnostic file path instead of printing the full plan repeatedly. A failed diagnostic write/analysis cannot replace the original computation exception; the job still fails and scratch write configuration is restored. No source rows are printed by this diagnostic. The plan can contain `External engine query` text, but adaptive execution can change the query actually sent.

Databricks `*** WARNING: max output size exceeded, skipping output. ***` means displayed/captured console text was clipped. The producer does not consume its own stdout or job-output API as input, so that warning does not truncate persisted result rows, change calculations or mark a failed task successful. Platform-generated exception traces can still hit UI output limits; use the full diagnostic file where available. This is separate from Statement Execution API `manifest.truncated`: that result/metadata condition remains an explicit failure, never an accepted incomplete result.

### Targeted Cancellation Read Path

ACC run 147418417090248 supplied the decisive native scan: the 16.4 job-compute connector generated `FROM pbi.dbx_fact_o2c_-_self_service_-_sales_orders` without quoting the table name. Columns were quoted correctly; the table-name hyphen caused Synapse's parse error. Adding Spark SQL backticks was already done and did not fix the remote FROM clause. A query-scoped dbtable override was tested in DEV and explicitly rejected as a forbidden dynamic foreign-table option. No shared foreign catalog, connection or source-table metadata is changed by this workaround.

Only `ds_cancellations_detail_7d` is evaluated through the existing target SQL warehouse (`--warehouse-id` comes from the already configured dashboard warehouse variable). Its original producer SQL, business-date freeze, predicates, raw columns, joins and native dashboard date filters are unchanged. The warehouse uses the properly quoted remote-table path and writes directly to the same batch's uniquely reserved scratch directory using documented `INSERT OVERWRITE DIRECTORY ... USING PARQUET`. The job reserves a new empty path with exist_ok=False first; an existing path cannot be overwritten or reused. Spark reads the completed files after verifying their native field names/types, then performs the same Delta write/read multiset parity, receipt and publication checks. No data is downloaded to the driver, no temporary Unity Catalog table or new output relation is added, and other datasets remain on the normal Spark path.

Before any result/state writes or long dataset calculations, the warehouse preflight verifies same validated workspace, the exact same current_user identity as Spark, CAN_USE/API access, source query analysis and quoted O2C remote FROM in EXPLAIN FORMATTED. It refuses missing/unquoted/incomplete plan metadata. Cancellation is the first dataset; other plans retain their relative order. API requests have bounded waits (identity 60s, EXPLAIN 120s, calculation 600s, including queue time), and failures cancel only the submitted statement where possible. Unconfirmed cancellations are logged; failed scratch remains for investigation and cannot publish. The job identity needs CAN_USE on the existing warehouse plus its existing source and target-volume access. No consumer permission or warehouse ACL is applied by this code, and no fallback to a human identity or the broken job-compute read is allowed. This avoids waiting for seven other datasets before detecting this known boundary problem, but it does not guarantee total job duration or first-run success.

`scripts/diagnose_cancellation_sql.py` performs DEV-only bounded EXPLAIN and one-row SELECT probes without modifying data objects. DEV native checks verify that the exact cancellation SELECT plan quotes the remote O2C table, the volume INSERT command compiles, and all 11 required O2C source columns can be read. The INSERT EXPLAIN exposes its logical input rather than optimized External engine query text, so SELECT quoting and INSERT compilation are checked separately. Local fixtures execute the full original cancellation SQL via SQL-to-Parquet and compare duplicate/NULL/decimal/join/date-range semantics exactly. These checks do not certify the complete warehouse write under the ACC/PRD job identity, actual target warehouse access, queue time, all live source data or end-to-end publication; those remain native acceptance requirements after promotion.

Each published gold result is backed by a silver Delta table using the `SC_BI_industry_sales_calc_` prefix and the internal `__industry_snapshot_id` marker. Consumer gold names use `SC_BI_industry_sales_<dashboard>_<dataset>_<component>`. D appends `_dev`; T/A/P use unsuffixed names in their target catalogs. Exact write/read multiset equality is checked for every result, including duplicates and NULLs, before the single `gold.SC_BI_industry_sales_dashboard_result_state` pointer publishes the batch. Receipts must match every expected dataset/table identity. Empty results are allowed only as the actual output of a successful computation; incomplete or failed computations cannot publish.

Until all 18 active datasets and 21 unique persisted relations verify, readers retain the previous completed batch. Initial views may exist but must not be considered ready before first publication. Existing owned views use `ALTER VIEW AS`, preserving consumer grants. Current and previous completed batches are retained; older/unpublished batches are deleted only after successful publication, with no VACUUM. A query lasting across more than one subsequent publication needs separate operational handling. This is atomic result-batch publication, not a transactionally consistent point-in-time snapshot of Synapse: sources are read sequentially. Mapping is updated in its own earlier task and is not included in the result pointer transaction.

The gold state records `snapshot_as_of_date`, `snapshot_completed_at`, and per-dataset result receipts with row counts/column names. Required result field/type changes fail and need reviewed migration. Logs identify each dataset/component, calculation start, verified result, and publication. Failure retains the old batch; operators must check its age. Job success alone does not certify viewer permissions, widget rendering, or an acceptable dashboard latency.

The native dashboard refresh tasks remain removed. Both native dashboard resources, pages, measures, widgets, filters and saved parameters remain. Reader ACLs now follow Noel's per-dashboard lists; existing manager/editor permissions remain. A legacy direct reader absent from that dashboard's approved list is omitted (Roberta's Open Orders entry), while matching direct readers remain. Consumer SQL reads the new gold results only, with no direct Synapse or legacy source-snapshot dependency. The job does not prepare native dashboard caches or subscription snapshots; interactive query execution and browser cache refresh remain separate.

Existing legacy raw tables, source views, state tables, allocation outputs, and old helper scripts are not dropped by this change. They are no longer produced or queried by the new job/dashboard graph. The permission manifest retires their declarations to match the new output inventory; this is not direct SQL revocation or deletion. The central permission pipeline's handling of removed declarations must be reviewed separately before retirement is considered complete. Do not run the legacy allocation/snapshot validation helpers as a test of this new flow.
